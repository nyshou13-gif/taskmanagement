# 第1章 インターネットとネットワークの仕組み

## Q1. インターネットとは
違う。インターネットは世界中のコンピューターネットワークをつなぐ通信基盤（道路のようなもの）。Webブラウザで見るホームページ（Web）は、その上で動くサービスの1つで、HTTPという約束事でページを配信する仕組み。メール、ファイル転送、オンラインゲームなどもインターネット上のサービスで、Webだけがインターネットではない。

## Q2. IPアドレスとポート番号
- `localhost` は「自分自身のコンピューター」を指す名前で、IPアドレスでは `127.0.0.1` に当たる。開発中は自分のPC内でフロントエンドとバックエンドを動かすため、これで接続できる。
- IPアドレスが「建物の住所」なら、ポート番号は「部屋番号」。1台のPCでは複数のプログラムが同時に通信を待ち受けるため、どのプログラムに届けるかを区別する必要がある。本アプリでは 5173 がフロントエンド（Vite）、8080 がバックエンド（Spring Boot）、5432 がデータベースの受付になっている。

## Q3. DNS
DNSは「ドメイン名からIPアドレスを調べる電話帳」。人間は `www.example.com` のような名前を覚えやすいが、コンピューターはIPアドレスでしか通信できない。入力後、ブラウザはまずDNSサーバーに「このドメインのIPアドレスは？」と問い合わせ、返ってきたIPアドレスのサーバーにHTTPSで接続してページを取得する。DNSがなければ、IPアドレスを直接入力する必要がある。

## Q4. HTTPとは
HTTP は HyperText Transfer Protocol の略で、ブラウザ（クライアント）とWebサーバーがデータをやり取りするための取り決め。「プロトコル」とは、通信するもの同士が共有する約束事・手順・形式のこと。「この形式で要求し、この形式で返事する」と決まっているから、異なる環境のブラウザとサーバーでも通信できる。

## Q5. HTTPとHTTPSの違い
HTTPSは、HTTPの通信をTLSで暗号化したもの。HTTPは通信内容が平文で流れるため、途中の経路で盗み見（盗聴）や改ざんができてしまう。HTTPSは暗号化に加え、証明書で「接続先が本物のサイトか」も確認できる。パスワードや個人情報を扱うサイトが当たり前になり、ブラウザがHTTPサイトに警告を出すようになったことや、証明書が無料で取れるようになったことで、ほぼすべてのサイトがHTTPSになった。

## Q6. リクエストとレスポンス
レストランに例える。客（クライアント）が注文（リクエスト）を出し、厨房（サーバー）が料理（レスポンス）を返す。注文がなければ料理は出てこないし、必ず客から話しかける。注文できないもの（存在しないメニュー）なら「ありません」という返事（エラー）が返る。Webでも、必ずクライアントから要求し、サーバーが結果を返す。

## Q7. HTTPメソッド
HTTPメソッドは「リクエストで何をしたいか」を表す動詞。図書館に例える。

| メソッド | 意味 | 例え | 本アプリでの例 |
|---|---|---|---|
| GET | 取得 | 本棚の本を見る・借りるリストを見る | タスク一覧の取得 |
| POST | 新規作成 | 新しい本を登録する | タスクの作成 |
| PUT | 全体を置き換え | 本の登録情報を全項目書き直す | タスクの全項目更新 |
| PATCH | 一部を更新 | 本の貸出状況だけ書き換える | ステータス（カラム）だけの変更 |
| DELETE | 削除 | 本を廃棄する | タスクの削除 |

## Q8. HTTPステータスコード
サーバーが結果を数字で知らせる仕組み。

- **200 OK**: 成功。要求どおりに処理できた。
- **201 Created**: 新しいリソースの作成に成功した（タスク作成のPOSTなど）。
- **400 Bad Request**: クライアントの要求が不正（タイトルが空、100文字超など入力エラー）。
- **404 Not Found**: 指定したリソースがない（存在しないタスクIDなど）。
- **500 Internal Server Error**: サーバー側の予期しないエラー（プログラムのバグ、DB障害など）。

先頭の数字で、2xx＝成功、4xx＝クライアント側の問題、5xx＝サーバー側の問題と大まかに分かる。

## Q9. JSONとは
JSON は JavaScript Object Notation の略で、`{"title": "資料作成", "priority": 2}` のように、キーと値でデータを表す軽量なテキスト形式。広く使われる理由は、①人間が読んで理解しやすい、②軽量で、③ほぼすべてのプログラミング言語が読み書きでき、言語の違うフロントエンド（TypeScript）とバックエンド（Java）の間でも変換しやすい、から。

## Q10. APIとは
API は Application Programming Interface の略で、「あるプログラムの機能を、別のプログラムから使うための窓口」。本アプリでは `/api/tasks` などがその窓口になる。フロントエンドが直接DBにアクセスしない理由は次のとおり。
- **セキュリティ**: DBの接続情報をブラウザに置くと、誰でも読み書きできてしまう。
- **ルールの集中管理**: 入力チェックなどの業務ルールをバックエンドに集められる。
- **変更に強い**: DBの構造を変えても、APIが同じなら画面を変えずに済む。

## Q11. CORSとは
CORS（Cross-Origin Resource Sharing）は、ブラウザが「別のオリジン（プロトコル・ドメイン・ポートの組）のサーバーへのアクセス」を制限し、サーバー側が許可したものだけ通す仕組み。悪意あるサイトが、ログイン中のユーザーのブラウザ経由で他サイトのAPIを勝手に叩くのを防ぐためにある。5173 と 8080 はポートが違うので別オリジンになり、そのままではブラウザにブロックされる。本アプリは開発時、Viteのプロキシで `/api` を8080へ転送することで、ブラウザからは同一オリジンに見せて回避している。

## Q12. クライアントとサーバー
クライアントは「サービスを要求する側」、サーバーは「要求に応えてサービスを提供する側」。役割で決まり、機器の種類では決まらない。
- **ブラウザ**: クライアント（ユーザーの代わりにバックエンドへ要求する）。
- **バックエンド**: ブラウザに対してはサーバー。DBに対してはクライアント（DBへ問い合わせる）。
- **データベース**: サーバー（バックエンドからの問い合わせに応える）。

# 第2章 Webアプリケーションの構造

## Q13. フロントエンドとバックエンド
フロントエンドはユーザーが直接触れる画面側、バックエンドは裏で動くデータ処理側。レストランの「ホール」と「厨房」の関係。
- **フロントエンド（React）**: ボード画面の表示、ドラッグ&ドロップ、入力フォーム、APIの呼び出し。
- **バックエンド（Spring Boot）**: APIの提供、入力チェック、業務ロジック（表示順の更新など）、DBへの保存・取得。

## Q14. 3層構造
役割ごとに分けると、次の利点がある。
- **変更の影響範囲が小さい**: 画面のデザイン変更はフロントエンドだけ、DBの変更はバックエンドだけで済む。
- **分担・再利用ができる**: 担当を分けて並行開発できる。同じAPIをスマホアプリからも使える。
- **安全**: DBをブラウザから直接触らせず、バックエンドで守れる。
- **テストしやすい**: 層ごとに単独でテストできる。

1つのプログラムにまとめると、どこを直しても全体に影響が出て、保守しにくく、秘密情報も守りにくくなる。

## Q15. データの流れ
1. ユーザーがフォームに入力して「作成」ボタンを押す。
2. フロントエンド（React）が入力をチェックし、`POST /api/tasks` をJSONで送る。
3. バックエンドのController がリクエストを受け取り、入力値を検証する（不正なら400を返す）。
4. Service が業務処理（表示順の決定など）を行い、Repository を通じてDBに `INSERT` を実行し、保存する。
5. DBが保存結果を返し、バックエンドが作成したタスクを `201 Created` でJSONで返す。
6. フロントエンドがレスポンスを受け取り、状態を更新して画面にカードが表示される。

## Q16. エンドポイントとURL設計
REST という考え方で、URLは「操作」ではなく「リソース（もの）」を表し、操作はHTTPメソッドで表す。
- `/api/tasks`: タスクの集まり。`GET` で一覧、`POST` で作成。
- `/api/tasks/{id}`: 特定の1件。`GET` で取得、`PUT`/`PATCH` で更新、`DELETE` で削除。

`{id}` は、対象のタスクを特定する識別番号が入るパス変数（例: `/api/tasks/5` なら5番のタスク）。名詞で統一することで、URLを見ただけで何のAPIか分かる。

## Q17. 同期処理と非同期処理
- **同期**: 電話のように、相手が答えるまで他のことをせずに待つ。
- **非同期**: メールやチャットのように、送ったら別の作業を進め、返事が来たら対応する。

Webの通信はネットワークやサーバー次第で時間がかかる。同期で待つと、その間画面が固まり操作できなくなる。非同期なら、通信中も画面を操作でき、結果が返ってきたら画面を更新できる。fetch や `async/await` が使われる理由。

## Q18. SPA（シングルページアプリケーション）
従来のWebサイトは、リンクを押すたびにサーバーから新しいHTMLページを丸ごと受け取り、画面全体を読み込み直す。SPAは最初に1つのHTMLとJavaScriptを読み込み、その後はAPIでデータ（JSON）だけを取得し、画面の必要な部分だけをJavaScriptで書き換える。ページ遷移の読み込みがなく、アプリのような滑らかな操作ができる（本アプリのドラッグ&ドロップも画面がリロードされない）。一方、初回の読み込みが重くなりやすい点は弱点。

## Q19. 入力チェック（バリデーション）の多重防御
- **フロントエンドのチェック**: ユーザーへの即時フィードバックのためのもので、親切さのための機能。ブラウザ側のコードはユーザーが改変でき、`curl` などで画面を通さず直接APIを叩けるため、チェックを回避できる。
- **バックエンドのチェック**: データの最後の砦で、不正なデータを必ず防げる。ただし、これだけだと、入力ミスのたびに通信が必要で、使い勝手が悪い。

そのため、使いやすさ（フロント）と安全性（バックエンド）の両方で行う。DBの制約（NOT NULL、CHECKなど）も加えれば、さらに多重になる。

## Q20. エラーハンドリング
- 失敗を握りつぶさず、ユーザーに分かる形で知らせる（「通信に失敗しました。再試行してください」など）。内部の詳細（スタックトレースなど）は見せない。
- ステータスコードに応じて対処を変える（400は入力を直してもらう、404は「見つかりません」、500や通信障害は再試行を促す）。
- 楽観的更新（ドラッグ後すぐに画面反映）をしている場合は、失敗時に元の状態に戻す。
- 一時的な障害には再試行やローディング表示を用意する。
- 原因調査のため、サーバー側ではログを残す。

# 第3章 データベースの基礎

## Q21. データベースとは
データを整理して保存し、検索・更新を効率よく安全に行えるようにした仕組み。ExcelやCSVと比べた優れた点は次のとおり。
- 多数のユーザー・プログラムが**同時に**読み書きしても壊れない（排他制御）。
- **大量データ**でも高速に検索できる（インデックス）。
- 制約（NOT NULL、外部キーなど）でデータの**整合性**を守れる。
- トランザクションで、途中で失敗したときに元へ戻せる。
- アクセス権限の管理やバックアップがしやすい。

## Q22. テーブル・行・列
- **テーブル**: Excelの「シート」。`tasks` テーブルは「タスクのシート」。
- **行（レコード）**: シートの「1行」。1件のタスク（例: id=1、タイトル「資料作成」、優先度2…）。
- **列（カラム）**: シートの「列見出し」。データの項目（`id`、`title`、`priority`、`due_date` など）。

| id | title | priority | due_date |
|---|---|---|---|
| 1 | 資料作成 | 2 | 2026-12-01 |
| 2 | レビュー依頼 | 3 | （空） |

## Q23. 主キー（PRIMARY KEY）
テーブルの中で行を一意に特定するための列で、重複せず、空（NULL）にもならない。本アプリの `tasks.id` は自動採番（`GENERATED ALWAYS AS IDENTITY`）の主キー。必要な理由は、「タスクの内容（タイトル）が同じ行」がありえても、更新・削除の対象を間違えずに指定できるようにするため（`/api/tasks/{id}` の `{id}` に対応）。また、他テーブルから参照する際のキー（外部キー）にもなる。

## Q24. CRUD操作
CRUD は Create（作成）・Read（読み取り）・Update（更新）・Delete（削除）の頭文字で、データ操作の基本の4つ。

| 操作 | HTTP | 本アプリの機能 |
|---|---|---|
| Create | POST | タスクの作成 |
| Read | GET | ボード（タスク一覧）の表示、タスク詳細の表示 |
| Update | PUT / PATCH | タスクの編集、ステータス変更、ドラッグ&ドロップでの移動 |
| Delete | DELETE | タスクの削除 |

## Q25. データの制約
制約は、不正なデータがDBに入らないようにするルール。
- **NOT NULL**: 空（値なし）を許さない。例えば `title` が空のタスクが保存されるのを防ぐ。
- **DEFAULT**: 値が指定されなかったとき、自動で入る初期値。例えば優先度を指定しなくても、既定の値が入る（本アプリの実装では `priority INTEGER NOT NULL DEFAULT 2`、つまり「中」を表す数値。設問の `'medium'` と同じ意図）。

アプリのバグや、APIを経由しない操作があっても、DBが最後の砦としてデータの正しさを守る。

## Q26. インデックス
本の巻末にある「索引」と同じ。索引がなければ、特定の語を探すために全ページをめくる必要があるが、索引があれば該当ページにすぐ飛べる。DBでも、インデックスがあると全行を調べずに目的の行を高速に探せる。ただし、インデックス自体の保存領域が必要で、更新のたびにインデックスも更新するため、書き込みが少し遅くなる。そのため、よく検索する列にだけ作る。本アプリでは `tasks (column_id, position)` にインデックスがあり、「カラムごとの表示順の取得」を高速にしている。

## Q27. トランザクション
複数の処理を「全部成功するか、全部なかったことにするか」のどちらかにまとめる仕組み。銀行の振込（Aから引き落とし＋Bへ入金）が、片方だけ成功してはいけないのと同じ。

ドラッグ移動では、移動したタスクの `column_id` と `position` の更新に加え、移動元・移動先の他のタスクの `position` も振り直す。途中でエラーが起きて一部だけ反映されると、表示順が重複したり欠けたりして、ボードが壊れる。トランザクションにすれば、失敗時はすべて元に戻る。本アプリでも Service 層に `@Transactional` を付けている。

## Q28. SQLとORM
- **SQL**: DBを操作するための言語（`SELECT * FROM tasks WHERE column_id = 1` のように、データの取得・追加・更新・削除をする）。
- **ORM（Object-Relational Mapping）**: DBのテーブルとプログラムのオブジェクト（Javaのクラス）を対応づけて、SQLを直接書かずにDB操作できるようにする仕組み。本アプリでは JPA（Hibernate）が該当し、`Task` クラスの操作がSQLに変換される。

ORMの利点は、生産性の向上と、パラメータバインドによるSQLインジェクション対策がしやすいこと。注意点は、複雑なクエリや性能問題では、背後のSQLを理解していないと対処できないこと。

# 第4章 開発プロセスとチーム開発

## Q29. バージョン管理（Git）
ファイルの変更履歴を記録し、「いつ・誰が・何を・なぜ」変えたかを管理する仕組み。必要な理由は、過去の状態に戻せる、複数人が同時に開発しても変更を統合できる、変更の経緯を追跡できるから。使わないと、`final_最新_本当に最終.zip` のようなファイルが増える、同じファイルを同時に編集して他人の変更を上書きしてしまう、不具合の原因となった変更が分からず、戻せない、といった問題が起きる。

## Q30. ブランチとPull Request
- **ブランチ**: 開発の流れを枝分かれさせたもの。本流（master/main）に影響を与えずに、独立して作業できる。
- **Pull Request（PR）**: ブランチの変更を本流に取り込んでほしいという依頼。目的は、変更内容の**レビュー**（バグや設計の問題を事前に見つける）、議論や記録の場、自動テストの実行、取り込み前の確認。
- **直接変更しない理由**: mainは常に動く状態で保つべきもの。レビューなしに全員が直接変更すると、バグや未完成のコードが混入し、全員に影響する。誰が何を変えたかも追いにくくなる。

## Q31. コミットメッセージの重要性
コミットメッセージは、変更の理由を未来の自分やチームに伝える記録。`feat: ログイン機能を追加` のように、種類と内容が分かると、履歴を見るだけで何が行われたか把握できる。不具合が起きたときに、原因となった変更を探しやすく、レビューもしやすい。また、変更履歴やリリースノートを自動で作る際の材料にもなる。「修正」「更新」だけでは、後から何も分からない。本プロジェクトでも、`<type>: 要約` と `Refs #Issue番号` を必須にして、変更とIssueを追跡できるようにしている。

## Q32. なぜ技術的な仕組みを理解すべきか
（下書き。ご自身の考えに合わせて書き換えること）

AIがコードを書けるようになっても、仕組みを理解する必要はあると考える。理由は3つある。

1. **AIの出力を評価するのは人間の責任だから。** AIは、もっともらしく動かないコードや、脆弱なコード（入力チェック不足、不要に広いCORS許可など）も書く。レビューして採否を決めるには、何が正しいかを判断する知識が必要。
2. **問題が起きたとき、原因を切り分けられるから。** 画面にデータが出ない原因が、フロントエンド、API、DBのどこにあるのか（ステータスコードは何か、CORSか、データがないのか）を判断できなければ、AIに的確に質問することもできない。
3. **良い指示を出せるから。** 「3層に分ける」「トランザクションでまとめる」「DBにも制約を付ける」といった設計の言葉を知っていれば、AIにより正確な指示を出せ、結果の質も上がる。

AIは「速く書く道具」で、「何を作るべきか、それが正しいか」を決めるのは理解している人間。道具が強力になるほど、使う側の理解の差が結果の差になると考える。
